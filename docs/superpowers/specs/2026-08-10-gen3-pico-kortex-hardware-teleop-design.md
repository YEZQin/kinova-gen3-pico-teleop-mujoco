# PICO 手柄控制 Kinova Gen3 实机：受保护遥操作设计

日期：2026-08-10

状态：设计已由用户批准，等待文档复核后进入实施计划

目标分支：`feat/kortex-hardware-merge`

## 1. 目标与成功标准

在保留现有 MuJoCo 遥操作能力的前提下，为项目增加 Kinova Gen3 Ultra 7DoF 实机后端，使 PICO 左手柄能够通过相对位姿映射控制机械臂末端的六自由度运动。

第一阶段成功标准：

- 默认启动仍是 MuJoCo；实机模式必须同时提供 `--backend kortex` 和 `--enable-hardware`。
- PICO 左手柄经 Unity OpenXR 发送 UDP 数据，现有 release-first 相对映射逻辑保持一致。
- Grip 未释放、未重新按下并完成锚定前，机械臂不得运动；首次按下不得产生跳变。
- 实机使用 Kortex 高层 TCP 通道和 Single Level Servoing，不使用低层 UDP 伺服。
- 位置与姿态误差转换为有界末端笛卡尔速度；不把 MuJoCo IK 用于实机控制。
- Grip 释放、PICO 数据失效或过期、源变化、Kortex RPC/网络异常、工作空间越界、主循环停滞、`Ctrl+C` 均触发显式 `Stop()`。
- 视觉模块不参与第一阶段控制；夹爪只允许只读探测，写控制保持关闭。
- 现场完成毫米级平移、小角度旋转和全部停止路径验证后，才认为实机遥操作可用。

## 2. 已知环境与边界

目标设备是带视觉模块和夹爪的 Gen3 Ultra 7DoF，Web 管理地址为 `192.168.1.10:80`。历史现场记录显示机器人型号族为 `MODEL_ID_L53`，固件为 `2.8.0-5`，配套 Python Kortex SDK 为 `2.8.0.post5`，Python 为 3.11.15，TCP 控制端口为 10000。历史记录只能用于准备，不能替代每次上电后的现场复核。

实机试验前应观察到：

- Operating Mode 为 `Running`；
- Servoing Mode 为 `Single Level servoing`；
- 机械臂无故障，反馈值有限且合理；
- 控制环境与机器人固件、SDK 版本匹配。

Web 页面显示的 `Arm Servoing - Manually Controlled` 和 `Angular Joystick` 是当前人工控制状态的观测值，不作为软件能够安全接管的充分条件。

第一阶段明确不包含：

- 夹爪开合写命令；
- 视觉闭环或视觉流处理；
- 自动执行 Home、Action 或预录轨迹；
- 低层关节电流/力矩控制；
- 自动重连后恢复运动；
- 绕过 Kortex 安全状态、看门狗或人工确认。

## 3. 代码基线选择

实现以 `origin/main` 的完整 PICO UDP/MuJoCo 链路和 `feat/kortex-hardware-merge` 中已有的受保护 Kortex 后端为基础。该分支已经包含后端抽象、Kortex 连接层、运动租约、预检、工作空间约束、看门狗和相应测试，能够最大限度复用已经审查过的安全语义。

当前根工作树上的旧 `main`、用户未跟踪资源以及 `codex/kinova-only-joint-speed` 中的实验性修改都不作为实现基线，也不得覆盖。实验分支只可用于查阅历史现场证据或提取经重新测试的独立修复。

最终集成通过差异审查完成，不强行重写历史，不清理与本任务无关的用户文件。

## 4. 系统架构

数据与控制路径如下：

```text
PICO 左手柄
  -> Unity OpenXR
  -> UDP :15031
  -> PicoUdpInput（解析、校验、源锁定、新鲜度）
  -> RelativePoseMapper（release-first、锚定、相对 6DoF 目标）
  -> TeleopController（状态机与后端编排）
  -> KortexBackend（反馈、位姿误差、限速、看门狗、Stop）
  -> Kortex TCP :10000 / Single Level Servoing
  -> Gen3 末端执行器
```

`MujocoBackend` 继续实现仿真控制。`KortexBackend` 与其共享意图层和安全状态机，但不共享 MuJoCo 的 IK、关节积分或仿真时间假设。

### 4.1 组件职责

`PicoUdpInput`

- 只负责 UDP 数据解析、数值有限性与范围校验、单一发送源锁定、序列/时间新鲜度。
- 不连接机器人，不发运动命令。

`RelativePoseMapper`

- 实现 Grip 先释放、后按下的武装逻辑。
- Grip 首次有效按下时同时记录控制器位姿和机器人末端位姿作为锚点。
- 输出相对目标位姿；重新捏合时从当前实际末端位姿重新锚定。
- 不处理传输、速度控制或安全停机。

`KortexConnection`

- 创建并按顺序关闭 TCP transport、Router、Session 与 Kortex clients。
- 密码只从 `KINOVA_PASSWORD` 环境变量读取；不得写入命令行、日志、配置或异常消息。
- 连接建立前不执行 Home、Action、夹爪或运动命令。

`KortexBackend`

- 使用 `BaseCyclic` 读取末端反馈。
- 计算当前位姿到目标位姿的平移误差和最短弧四元数姿态误差。
- 将误差转换为有界线速度和角速度，并通过高层 Kortex twist 接口发送。
- 独立看门狗监视主循环心跳；负责幂等 `Stop()`、故障锁存和资源清理。

`TeleopController`

- 组织输入、映射、预检、后端和状态转换。
- 不绕过任何后端安全门，也不在异常后自动恢复 ACTIVE。

`HardwareAdmission`

- 要求显式硬件双开关、匹配 SDK、实时只读预检、现场检查清单和精确输入 `MOVE`。
- 人工确认前要求 Grip 已释放；确认后才允许建立可写 Kortex 会话。

## 5. 实机控制律与边界

实机控制采用有界末端速度伺服：

- 平移：`v = clamp(Kp_position * position_error, max_linear_speed)`；
- 旋转：将目标与当前四元数之差转换为最短弧旋转向量，再计算 `w = clamp(Kp_rotation * rotation_error, max_angular_speed)`；
- 所有输入、反馈和中间结果必须为有限值；任何 NaN/Inf 直接触发故障停机；
- 到达小误差死区时发送零速度或执行 Stop，不依赖命令 duration 自动停机。

第一轮实机方向性验证使用固定的保守参数上限：

- 控制频率：40 Hz；
- PICO 相对位移比例：0.25；
- 最大线速度：0.005 m/s；
- 最大角速度：2 deg/s；
- PICO 数据过期阈值：0.2 s；
- 主循环到宿主机发起 `Stop()` 的看门狗上限：0.2 s；
- 相对锚点工作空间：每个平移轴不超过 ±0.02 m；
- 相对锚点姿态偏差：不超过 5 deg。

启动时还必须提供并审查绝对笛卡尔工作空间边界。边界必须包含当前锚点，且不得扩大上述第一轮相对包络。超出边界时不做静默裁剪，而是 `Stop()`、锁存故障并退出。

0.2 s 是宿主机发现停滞并发起停止请求的设计上限，不代表机器人从任意速度物理停止所需的保证时间。实际停止距离和时间必须现场测量。

## 6. 安全状态机

```text
START
  -> WAIT_FRESH_PICO
  -> WAIT_GRIP_RELEASE
  -> READ_ONLY_PREFLIGHT
  -> WAIT_PHYSICAL_CHECKLIST_AND_MOVE
  -> CONNECT_KORTEX
  -> READY
  -> GRIP_PRESS_AND_ANCHOR
  -> ACTIVE
```

正常重新捏合路径：

- `ACTIVE` 中 Grip 释放：立即请求 `Stop()`，进入 `READY`；
- 只有输入持续健康且 Grip 再次有效按下时，才以当前控制器和当前末端反馈重新锚定并返回 `ACTIVE`；
- 锚定发生的同一周期不得输出非零运动命令。

锁存故障路径：

- PICO 数据过期、格式非法、非有限值或发送源变化；
- Kortex RPC、反馈、网络或会话异常；
- 工作空间越界或姿态包络越界；
- 主循环心跳超时；
- `Stop()` 返回异常或无法确认调用完成。

上述任一事件都执行尽力而为且幂等的 `Stop()`，锁存故障，拒绝自动重连和自动恢复，并以非零状态退出。若 Stop 请求本身失败，操作者必须使用物理急停或 Web 界面介入。

`Ctrl+C` 与正常进程退出必须按以下顺序清理：

1. 请求 `Stop()`；
2. 关闭 Session；
3. 停止 Router；
4. 断开 TCP transport。

清理操作允许重复调用，但不得因前一项失败而跳过后续资源回收；所有失败都要保留原始上下文且不得泄露密码。

## 7. 启动准入与人工责任

实机模式的准入顺序必须 fail-closed：

1. 验证 `--backend kortex` 与 `--enable-hardware` 同时存在；
2. 验证 Python、Kortex wheel 和 protobuf 组合可导入且与固件匹配；
3. 在不连接机器人可写会话的情况下，检查 CLI 参数、工作空间和密码环境变量存在性；
4. 收到新鲜 PICO 数据，确认当前 Grip 已释放，并锁定唯一 UDP 源；
5. 执行实时只读预检：机器人身份族、固件、servoing mode、operating mode、故障、末端反馈；
6. 操作者逐项确认现场物理条件，并精确输入 `MOVE`；
7. 才建立 Kortex 会话，并保持 `READY` 直到 Grip 按下锚定。

每次现场运行都必须重新确认：

- 机器人固定可靠，工作空间清空；
- 物理急停可触达且已由旁站人员掌握；
- 操作者与旁站人员均不在机械臂扫掠范围；
- 使用可信有线网络，PICO、控制主机与机器人网络路径稳定；
- Web 页面状态与预检结果一致；
- Grip 在确认和连接前保持释放；
- 首轮只做单轴、毫米级、短时动作。

历史日志中的“已确认”不得跨会话复用。

## 8. 凭据、日志和隐私

- 用户名可使用非敏感默认值或显式参数；密码仅来自 `KINOVA_PASSWORD`。
- 启动日志只记录密码是否提供，不记录其内容、长度或派生值。
- 异常和诊断包不得包含密码、Authorization 字段、完整网络抓包、机器人序列号或 MAC 地址。
- 日志应记录后端、限速、控制频率、过期阈值、工作空间摘要、状态转换、Stop 原因和资源清理结果。
- 夹爪探测结果若不确定，应记录为 `unknown-disabled`；绝不据此尝试写控制。

## 9. TDD 与验证策略

实施阶段先审计 `feat/kortex-hardware-merge` 的已有行为，再只为设计与现状之间的缺口编写失败测试。每个缺口遵循 RED、GREEN、REFACTOR，禁止为通过测试而削弱 fail-closed 语义。

### 9.1 离线单元测试

- 双硬件开关、缺失凭据、非法 IP/端口、非法速率和非法工作空间在 SDK 导入或网络连接前失败；
- UDP 解析、有限值、源锁定、新鲜度、Grip release-first 与首次锚定无跳变；
- 平移和四元数姿态误差计算、最短弧、死区、限速和单位换算；
- 相对与绝对工作空间边界，越界必须锁存停机而非裁剪；
- Grip 释放、数据过期、输入异常、主循环停滞都恰好触发所需 Stop 语义；
- `Stop()` 幂等，清理顺序正确，清理失败被报告；
- 夹爪和视觉写路径不可达；
- 日志与错误消息不含密码。

### 9.2 模拟 Kortex 集成测试

使用 mock clients 验证：

- 连接和资源回收顺序；
- 只读预检失败时零写调用；
- 人工确认前零连接或零运动调用；
- `SendTwistCommand` 的参考系、数值、频率和上限；
- RPC/反馈/网络异常时 Stop、故障锁存和非零退出；
- watchdog 与主循环并发条件下不会遗漏 Stop；
- 自动重连或异常后自动恢复不会发生。

### 9.3 回归与质量门

- 原有 MuJoCo 测试全部通过，默认命令行为保持仿真；
- Python 测试套件全部通过，新增/修改模块覆盖率不低于 80%；
- 静态检查、格式检查和 `git diff --check` 通过；
- 使用目标 Python 3.11 环境完成 Kortex SDK 导入测试；
- 安全审查确认无硬编码密钥、无可达的未授权写路径、无静默异常吞掉；
- 文档命令和 CLI `--help` 与代码一致。

## 10. 分阶段现场验收

任何阶段失败都回到停机状态，不跳级。

### T0：只读连接，无运动

- 完成本次上电的物理检查；
- 核对 SDK/固件、Running、Single Level Servoing、故障状态和有限反馈；
- 验证没有 Home、Action、twist 或夹爪写调用；
- 保存去敏后的只读报告。

### T1：武装与无跳变，无持续运动

- 验证 Grip 未先释放时不能武装；
- 验证确认前和 Kortex 会话建立前 Grip 必须释放；
- 验证首次按下只锚定，末端无可见跳变；
- 松开 Grip 后观察 Stop 请求和机器人静止。

### T2：方向性微动

- 采用本设计的首轮限速和工作空间；
- 依次执行 X/Y/Z 单轴毫米级平移，再执行 Roll/Pitch/Yaw 小角度旋转；
- 每个方向单独记录手柄输入方向、末端反馈方向、峰值速度、Stop 原因与人工观察；
- 任一轴符号、参考系或耦合不符即停止，不继续组合运动。

### T3：停止与故障注入

- 分别验证 Grip 释放、PICO 数据中断/过期、受控网络异常、进程 `Ctrl+C` 和 watchdog 停滞路径；
- 测量从事件发生到宿主机 Stop 请求、速度开始下降和反馈静止的时间；
- Stop 失败、机器人继续运动或程序自动恢复均判定失败，并要求物理急停/Web 介入。

只有 T0-T3 都有本次设备、本次软件版本的证据，才能把第一阶段标记为“实机遥操作已验证”。离线测试通过只能表述为“软件准备就绪”，不能表述为“实机安全已证明”。

## 11. 实施与交付顺序

1. 复核并批准本设计文档；
2. 基于现有集成分支编写逐文件 TDD 实施计划；
3. 运行基线测试，审计现有实现与设计差距；
4. 以失败测试驱动补齐差距；
5. 完成代码、安全和文档审查；
6. 先执行 T0，只读证据通过后再由操作者单独批准进入运动阶段；
7. 在现场逐级执行 T1-T3，保存去敏证据；
8. 验证稳定后再设计夹爪控制，夹爪不得与本阶段同时解锁。

本设计不授权当前文档阶段连接或驱动机器人；实机运动仍需在运行当次完成所有准入门并由现场操作者确认。
